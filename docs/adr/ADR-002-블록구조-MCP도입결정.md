# ADR-002: 블록구조 및 MCP 도입결정

## 상태
Accepted

## 결정 시점
2026-02-11

## 배경
개발 세션은 보통 5~8시간 이상 지속되며, 수많은 잡담, 에러 로그, 코드 수정 내역이 뒤섞여 있다. 이를 단순히 텍스트로 요약하거나 전체 로그를 LLM에 입력하여 회고록을 작성하는 방식은 다음과 같은 한계가 있었다.

-   **토큰 한계 및 비용:** 전체 로그를 입력하면 LLM의 Context Window를 초과하거나 불필요한 비용이 발생한다.
-   **맥락(Context)의 소실:** 단순 요약문은 "어떤 에러 로그 때문에 이 코드를 수정했는지"에 대한 구체적인 인과관계를 잃어버린다.
-   **사용자 제어권 부재:** AI가 작성한 글을 사용자가 수정하고 싶어도, 근거 데이터(원본 메시지)에 접근하기 어려워 단순 텍스트 편집에 그쳐야 했다.

## 결정
단순 텍스트 요약 방식을 폐기하고, **메시지 ID 매핑 정보를 포함한 계층적 JSON 블록 구조**를 도입하며, 이를 생성하기 위해 **MCP(Model Context Protocol)** 개념을 적용한다.

1.  **데이터 구조 (SessionBlock):**
    -   회고록의 뼈대가 되는 `Block` (대주제) > `Topic` (소주제) > `Message IDs` (원본 연결)의 3단계 계층 구조를 정의한다.
    -   각 소주제는 `PROBLEM`, `CAUSE`, `SOLUTION`, `TRIAL` 등의 명시적인 타입을 갖는다.
2.  **AI 역할의 변화 (Agentic Workflow):**
    -   AI는 단순히 글을 쓰는 것이 아니라, 대화 로그를 읽고 `create_block`, `add_message` 등의 도구(Tool)를 사용하는 **MCP Agent**로서 데이터를 구조화한다.
3.  **큐레이션 기반 생성 (Curation-based Generation):**
    -   사용자는 AI가 구조화한 블록을 UI에서 선택(Check)하고 힌트(Marking)를 준다.
    -   최종 글 작성 시에는 **선택된 메시지의 원본만 Lazy Loading**하여 LLM에 입력한다.

## 이유
-   **토큰 효율성 극대화:** 8시간의 로그 중 실제 회고에 필요한 핵심 메시지(약 5~10%)만 선별하여 LLM에 보내므로 비용과 속도 면에서 유리하다.
-   **Fact Grounding (근거 기반):** 요약된 텍스트가 아니라 원본 코드와 로그를 기반으로 글을 작성하므로 할루시네이션이 최소화된다.
-   **사용자 경험(UX) 혁신:** 사용자는 백지에서 글을 쓰는 것이 아니라, AI가 정리해둔 '목차'를 보고 필요한 재료만 골라 담는 경험을 하게 된다.

## 결과
-   **DB 스키마:** `session_block` 테이블에 `content_json` 컬럼을 추가하여 계층적 데이터를 저장한다.
-   **UI 개발:** 텍스트 에디터 이전에, 블록을 선택하고 필터링할 수 있는 **'큐레이션 패널(Accordion UI)'**을 우선적으로 개발한다.
-   **AI 로직:** 프롬프트 엔지니어링을 통해 AI가 정해진 JSON 스키마를 준수하도록 강제한다.

## 후속 작업
-   [ ] 메시지 리스트를 입력받아 JSON 블록을 반환하는 System Prompt 작성
-   [ ] JSON 구조를 매핑할 `SessionBlock` 엔티티 및 DTO 구현
