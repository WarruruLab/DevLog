# ADR-001: 개발로그 구체화

## 상태
Accepted

## 결정 시점
2026-02-11

## 배경
프로젝트 초기 기획 단계에서부터 **DevTalk(데이터 생산)**와 **DevLog(데이터 가공)**는 서로 다른 트래픽 패턴과 리소스 요구사항을 가진 별개의 시스템으로 정의되었다.

- **DevTalk:** 실시간성이 중요한 채팅 서비스 (Low Latency)
- **DevLog:** 대량의 로그 분석과 AI 연산이 필요한 회고 서비스 (High Compute)

이번 Phase 3 개발에 착수하면서, 추상적이었던 두 서비스 간의 연동 방식과 DevLog의 내부 처리 흐름을 구체적인 구현 수준으로 정의해야 했다. 특히 8시간 이상의 긴 세션 데이터를 어떻게 효율적으로 처리하고, 사용자에게 가치 있는 결과물로 전달할 것인지에 대한 명확한 워크플로우가 필요했다.

## 결정
기존의 분리 원칙을 유지하며, **Pull Model 기반의 단방향 데이터 파이프라인**과 **3단계 처리 프로세스(3-Phase Process)**를 DevLog의 핵심 아키텍처로 확정한다.

1.  **서비스 간 인터페이스 (Interface):**
    -   DevLog가 주도권을 갖고 DevTalk의 `Internal API`를 호출하여 데이터를 가져오는 **Pull Model**을 채택한다.
    -   `last_analyzed_at` 커서(Cursor)를 사용하여 중복 분석을 방지하는 **Incremental Fetching**을 구현한다.
2.  **3-Phase Workflow:**
    -   **Phase 1 (Sync & Structure):** 데이터 수집 및 AI를 통한 JSON 블록화 (비동기 처리)
    -   **Phase 2 (Curation):** 사용자 개입을 통한 블록 선택 및 해결책 마킹 (Human-in-the-loop)
    -   **Phase 3 (Generation):** 선택된 데이터 기반의 Markdown 초안 생성 (Lazy Loading)

## 이유
-   **관심사의 완벽한 분리:** 채팅 서버(DevTalk)는 데이터 서빙에만 집중하고, 복잡한 분석 부하(DevLog)로부터 격리되어 안정성을 보장받는다.
-   **데이터 무결성:** 원본 데이터는 DevTalk에 보존하고, DevLog는 이를 복제하여 가공하므로 원본 훼손의 위험이 없다.
-   **유연한 확장성:** 향후 DevTalk 외에 Slack, GitHub 등 다른 데이터 소스를 추가하더라도 '수집(Sync)' 단계만 구현하면 동일한 파이프라인을 태울 수 있다.

## 결과
-   **DB 스키마:** DevLog는 원본 미러링을 위한 `synced_message` 테이블과 분석 결과를 담는 `session_block` 테이블을 갖는다.
-   **API 구현:** DevTalk는 내부 시스템용 데이터 제공 API(`GET /messages`)를, DevLog는 이를 주기적으로 호출하는 `SyncService`를 구현한다.
-   **개발 로드맵:** MVP 단계에서는 이 파이프라인의 '연결'과 '흐름'을 완성하는 것에 집중한다.
