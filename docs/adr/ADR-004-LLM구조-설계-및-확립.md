# ADR-004: LLM구조 설계 및 확립

## 상태
Accepted

## 결정 시점
2026-02-19

## 배경
DevTalk의 데이터를 수집하고 이를 AI로 분석하여 블로그 초안을 생성하는 DevLog의 LLM을 설계해야함

- **JDBC 생산성 및 편의성**: 단순 CRUD는 `?` 방식이 직관적이지만, 대량 저장(Batch)이나 파라미터가 많은 경우 순서 맞추기가 번거롭고 실수가 발생할 확률이 높음.
- **AI 연동 유연성 확보**: 특정 AI 모델(Gemini)에 코드가 강하게 결합될 경우, 향후 모델 교체나 테스트를 위한 Mock 객체 활용이 어려움.
- **계층 간 책임 분리**: `DraftService`가 비즈니스 로직(초안 생성 흐름) 외에 AI 프롬프트 구성 및 응답 파싱과 같은 세부적인 AI 로직까지 떠맡는 것은 객체지향적이지 않음.

## 결정
1. **Hybrid JDBC 접근법**: 단순 쿼리는 `JdbcTemplate`(`?`)을 사용하고, Batch Insert나 복잡한 파라미터가 필요한 경우 `NamedParameterJdbcTemplate`(`:name`)을 사용함.
2. **RestClient 도입**: `RestTemplate` 대신 Spring Boot 4의 권장 방식인 현대적인 **`RestClient`**를 사용하여 모든 외부 API(DevTalk, Gemini)와 통신함.
3. **인터페이스 기반 LLM 추상화**: DevTalk의 설계를 차용하여 `LlmClient` 인터페이스를 정의하고, 실제 구현체(`GeminiHttpClient`)는 `infra` 계층에 격리함.
4. **전용 AiService(AnalysisAiService) 계층 생성**: `DraftService`와 `LlmClient` 사이에 중간 레이어를 두어 프롬프트 엔지니어링 및 AI 응답 처리를 전담하게 함.

## 이유
- **실용적 생산성**: 개발자가 가장 편하게 느끼는 방식을 상황에 맞게 선택하여 구현 속도를 높이고 코드 가독성을 확보함.
- **기술적 현대화**: Spring Boot 4 및 자바 21 환경에 최적화된 `RestClient`를 사용하여 라이브러리 문제를 해결하고 더 세련된 코드를 유지함.
- **높은 유지보수성**: `LlmClient` 인터페이스를 통해 향후 Gemini 외에 OpenAI 등 다른 모델로의 전환을 용이하게 함.
- **명확한 관심사 분리**: `AiService`를 도입함으로써 각 서비스가 자신의 비즈니스 목표(동기화, 초안 작성 등)에만 집중할 수 있는 환경을 조성함.
- **프로젝트 간 일관성**: DevTalk과 유사한 AI 연동 아키텍처를 유지함으로써 개발 경험을 통일하고 코드 재사용성을 높임.

## 결과
- **구조적 견고함**: `infra.client`와 `domain.llm` 패키지를 통해 외부 통신 및 AI 인터페이스가 깔끔하게 정리됨.
- **코드 유연성**: `SyncService` 및 `DraftService`가 구현체에 의존하지 않고 인터페이스를 통해 동작하므로 테스트 및 확장이 자유로워짐.
- **운영 효율성**: 추가 의존성 없이도 로컬과 배포 환경의 설정을 안전하게 관리할 수 있는 구조가 마련됨.
- **미래 지향적 설계**: AI 기술 변화에 기민하게 대응할 수 있는 추상화 레이어가 확보됨.
