# ADR-003: DB구조 및 ERD 작성(개발톡의 session을 중심으로)

## 상태

Accepted

## 결정 시점

2026-02-11

## 배경

DevLog는 외부 서비스인 DevTalk의 대화 내용을 동기화하고, 이를 AI로 분석하여 회고록을 작성하는 서비스다. 데이터베이스 스키마를 설계하는 과정에서 다음과 같은 문제와 고민이 있었다.

1. **데이터 관계의 모호함**
   초기 ERD에서는 `SyncedMessage`와 `SessionBlock`을 직접 연결하려 했다. 그러나 "여러 메시지가 모여 하나의 블록이 된다(N:1)"는 직관과, "하나의 세션에서 여러 블록이 파생된다(1:N)"는 DB 구조 간의 괴리가 있어 관계 정의가 혼란스러웠다.

2. **외부 의존성 ID와 성능 이슈에 대한 이해 부족**
   DevTalk은 `UUID`를 PK로 사용하므로 이를 `synced_message`에 그대로 가져와야 한다. MySQL(InnoDB) 환경에서 UUID를 PK로 쓸 경우 성능 저하(Clustering Index 효율 저하)가 발생한다는 기술적 우려를 확인했으나, **현재 단계에서는 그 구체적인 원리를 명확히 이해하지 못한 상태다.** 따라서 섣불리 설계를 확정하기보다, 우선 도입 후 학습을 통해 검증하는 과정이 필요하다고 느꼈다. 도입 전과 후의 성능 차이를 비교해보겠다.

3. **데이터 독립성**
   DevTalk의 세션이 삭제되더라도 DevLog의 회고 기록은 유지되어야 할 수도 있다. 물리적인 Foreign Key 제약 조건이 시스템 결합도를 높일 우려가 있었다.

## 결정

우리는 **세션(Session)을 논리적 최상위 개념으로 두는 스키마**와, 데이터 성격에 따른 **하이브리드 ID 전략**을 채택한다.

### 1. 세션 중심의 관계 설계 (Session-Centric Schema)

- `SyncedMessage`와 `SessionBlock`을 직접 연결하지 않는다.
- 대신 두 테이블 모두 `session_id`를 공통 분모(논리적 부모)로 가지는 **형제(Sibling) 관계**로 정의한다.
- 모든 조회와 분석의 기준은 `session_id`가 된다.

### 2. 하이브리드 ID 전략 (Hybrid ID Strategy)

- **`synced_message` 테이블:** 외부 시스템(DevTalk)과의 정합성을 위해 일단 **UUID (String)** 를 PK로 사용한다. (추후 성능 검증 대상)
- **`session_block`, `draft` 테이블:** 내부 데이터이므로 관리가 용이한 **Auto Increment (BigInt)** 를 사용한다.

### 3. 논리적 외래키 사용 (Logical FK)

- `session_id` 컬럼에 대해 물리적인 FK 제약조건(`CONSTRAINT FOREIGN KEY`)을 걸지 않는다.
- 대신 애플리케이션 레벨에서 검증하고, DB 레벨에서는 **Index**를 통해 조회 성능만 확보한다.

## 이유

1. **비즈니스 로직과 구조의 일치**
   분석(Analysis) 행위는 '특정 메시지 한 줄'이 아니라 '대화의 흐름(Session)' 전체를 대상으로 이루어진다.

2. **현재 지식 수준에서의 최선 선택 (추후 검증)**

   - 내부 데이터(`session_block`, `draft`)에는 확실하게 안전한 **Auto Increment**를 적용하여 리스크를 줄인다.
   - 외부 데이터(`synced_message`)는 정합성을 위해 **UUID**를 쓰되, 이것이 실제로 성능에 어떤 영향을 미치는지 **추후 학습(Real MySQL 등)을 통해 원리를 파악하고 벤치마킹**하기로 한다.

3. **유연성 확보**
   물리적 FK를 제거함으로써 시스템 간 결합도를 낮췄다.

## 결과

- **ERD 구조 변경:** `session_id`를 중심으로 하는 스타 스키마(Star Schema) 형태와 유사해졌다.
- **학습 과제 도출:** 데이터베이스 인덱스 원리에 대한 학습 필요성이 공식적인 프로젝트 과제로 등록되었다.

## 후속 작업

- [ ] `synced_message` 테이블에 `(session_id, created_at)` 복합 인덱스 적용
- [ ] `session_block`, `draft` 테이블에 `session_id` 단일 인덱스 적용
- [ ] **[학습]** `Real MySQL 8.0`을 학습하여, UUID가 B-Tree 인덱스와 페이지 분할에 미치는 영향 분석하기
- [ ] **[검증]** 학습한 내용을 바탕으로 현재 스키마가 적절한지 재평가하고 필요시 수정 (Refactoring)
